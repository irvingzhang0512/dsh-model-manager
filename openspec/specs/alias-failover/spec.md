# F002 别名候选与失败回退

## Purpose

为 dsh-model-manager 的别名候选与失败回退维护唯一可编辑的行为与验收规格，保留原编号 F002，区分当前预期、尚未实现设计和历史验证；原始需求、项目资料及旧文档继续原位只读保留。

## Requirements

### Requirement: F002 别名候选与失败回退

系统 SHALL 按下列完整场景落实别名候选与失败回退的预期、边界与验收。本节迁入已有功能规则；本次仅迁移文档，没有重新执行产品验收。

#### Scenario: F002-S01 Desktop 契约

- **WHEN** 用户通过别名发起请求或管理候选
- **THEN** Desktop 契约：用户手动候选和固定五次／暂存／停止规则保持；新增候选级冷却、下一用户轮回首选、单一并发恢复租约、本轮成功模型固定及独立持久健康状态。默认临时故障 60 秒、限流 300 秒、额度 3600 秒；有效服务端等待优先，认证待凭据变化或手动恢复，本次能力不匹配不产生全局故障。完整规则及验收见 Desktop 契约第 4 节；旧 aliases.*.reliability 不复活。

#### Scenario: F002-S02 行为与边界

- **WHEN** 用户通过别名发起请求或管理候选
- **THEN** 具体 SPEC 与架构／配置契约提交审阅后，用户回复“继续实现”明确确认该版文档，据此开发，未新增语义范围。本增量独立于 F006 的待确认批量测试，原有差异保留。

#### Scenario: F002-S03 本次场景与预期

- **WHEN** 用户通过别名发起请求或管理候选
- **THEN** 本次场景与预期：别名按配置顺序遍历全部候选，每个具体 Provider＋Model 在一次请求内至多进入一次候选组，不受全局／别名旧 maxAttempts 的三次总上限限制。临时网络、超时、服务端故障每候选最多实际调用五次（首次加四次重试），退避为 0.5、1、2、4 秒；额度、限流、认证、参数、上下文和其他非临时错误立即进入下一候选。同 Provider 的后续不同模型仍尝试。

#### Scenario: F002-S04 别名范围

- **WHEN** 用户通过别名发起请求或管理候选
- **THEN** 别名范围：直接 alias 入口，以及 AUTO、视觉目标、旧有效绑定或会话覆盖最终解析到 @别名的请求，使用同一新规则；具体模型入口保持已有行为。当前配置仍须合法，空别名、无效逻辑入口和别名递归不作为候选错误绕过校验；单个候选不可用、参数准备失败或图片能力不匹配则记录原因并继续。

#### Scenario: F002-S05 输出与重做

- **WHEN** 用户通过别名发起请求或管理候选
- **THEN** 输出与重做：每次尝试先暂存文字、推理、工具调用、usage 和终止元数据；只有 stop、tool-calls 或 max-tokens 正常结束才提交该次完整输出。失败即丢弃该次全部暂存内容，重做当前模型请求；历史消息和已经完成的工具操作保留，不重跑整轮、不拼接不同尝试的输出。无终止标记的断流视为临时故障；每次暂存最多 32 MiB，超限不截断成成功，而是切下一候选。

#### Scenario: F002-S06 停止与快照

- **WHEN** 用户通过别名发起请求或管理候选
- **THEN** 停止与快照：用户停止立即终结等待，取消解析、流读取和退避，不再尝试候选；不配合取消的上游清理不阻塞返回，迟到内容不提交。请求开始固定配置、候选、能力、输入和参数，运行期间保存／清理设置不改正在执行的请求。

#### Scenario: F002-S07 长上下文

- **WHEN** 用户通过别名发起请求或管理候选
- **THEN** 长上下文：别名上下文错误仍尝试原别名后续候选，不再只准访问 @long-context；不隐式追加其他别名的候选。用户可将长上下文模型明确放入当前别名；具体模型的旧长上下文恢复策略保留。

#### Scenario: F002-S08 错误与日志

- **WHEN** 用户通过别名发起请求或管理候选
- **THEN** 错误与日志：全部候选失败时只返回一次 ALL_CANDIDATES_FAILED，列出尝试的 Provider／Model、次数和脱敏失败原因；取消返回 aborted，不伪装成候选耗尽。实际调用记录全局 attempt、候选序号 candidateIndex、候选内 candidateAttempt、错误码、耗时、用量和请求 ID；准备失败记 candidateAttempt=0，不冒充真实模型调用。失败尝试的用量留在逐次日志，成功输出仅携带该次 usage 与 replayState。

#### Scenario: F002-S09 设置与遗留配置

- **WHEN** 用户通过别名发起请求或管理候选
- **THEN** 设置与遗留配置：别名页移除旧 maxAttempts／retryTransient／parameterDowngrade 覆盖控件，展示固定规则及成功后显示完整回答的说明；不新增可调持久字段。全局 reliability 继续用于具体模型，不能再显示为控制别名。旧别名三个键不参与有效配置及校验，只在原始层保留待显式清理；独立预览／应用／恢复只删除这三个键，保留未知键、候选、推理映射、全局设置、凭据和全部引用。恢复旧值仍停用；普通保存不复活已清理值。技术契约见架构／配置同版节。

#### Scenario: F002-S10 本次验收

- **WHEN** 用户通过别名发起请求或管理候选
- **THEN** 本次验收：无 status 的 RATE_LIMIT／QUOTA 后第三候选成功；临时故障第五次成功、五次失败再切换、四个以上候选全部可达；同平台候选、准备失败、图片不匹配、上下文错误继续；半段文字／推理／工具调用失败不进入宿主，成功工具仅执行一次；解析／读取／退避／提交期间停止及时结束；缺 finish、32 MiB、全部失败聚合、快照和逐次日志；旧任意类型叶值、未知键、取消清理、应用／恢复／幂等／并发冲突及普通保存不复活。

#### Scenario: F002-S11 行为与边界

- **WHEN** 用户通过别名发起请求或管理候选
- **THEN** 停用的 auto.preferences 仅作为历史数据保留，不作为有效使用引用、不阻止别名／模型删除，也不随其他目录操作或官方迁移改写；明确清理通过 F005 独立操作完成。旧 auto.main／roles、视觉、宿主默认、原生 Subagent 和未来覆盖仍按现有规则检查。

#### Scenario: F002-S12 行为与边界

- **WHEN** 用户通过别名发起请求或管理候选
- **THEN** 具体 SPEC F002／F004／F009 和架构／配置契约交用户审阅后，用户以“继续实现”明确确认该版文档；实现与验证独立记录于 V1-COVERAGE。

#### Scenario: F002-S13 删除预览

- **WHEN** 用户通过别名发起请求或管理候选
- **THEN** 删除预览：点击删除别名先展示所有直接使用位置，包括旧 auto.main、AUTO 三档及规则、旧 roles、vision.target、宿主默认、原生 Subagent 范围及未来 session／nextTurn 覆盖；关闭功能后的遗留引用也要展示。每项明确替换或清除，未解决项阻止应用；不删除别名候选的真实模型、模型覆盖或其他别名。

#### Scenario: F002-S14 删除规则

- **WHEN** 用户通过别名发起请求或管理候选
- **THEN** 删除规则：启用中的 AUTO 必填执行档和宿主默认模型必须替换；其他普通引用可替换为已加载真实模型或清除。Subagent 范围允许移除该入口，但启用时仍需满足宿主非空范围约束。清除 Selection 目标同时移除 reasoningEffort、tier、thinking 等依赖目标的档位，保留独立 maxOutputTokens 及未知字段；旧主模型清除前说明旧 AUTO 入口将使用宿主默认模型。图片引用按 F004 处理，不因旧视觉兜底引用而关闭无关当前辅助模型。

#### Scenario: F002-S15 验收

- **WHEN** 用户通过别名发起请求或管理候选
- **THEN** 验收：无引用可删除；隐藏旧主模型和关闭后的旧视觉引用可在预览解决；必填引用不能清除，图片替换不能选仅文本／未知能力模型；删除和全部引用修改整体应用、回滚及恢复，进行中请求和历史不改写。并发 revision／目录／未来覆盖变化拒绝应用与覆盖恢复。

### Requirement: F002-Desktop 4. 别名冷却与回首选（F002／F008／F009）

系统 SHALL 遵守已确认并实现的 Desktop 契约；本节替代对应旧平台接口与旧默认表述，不恢复已退役能力。

#### Scenario: F002-Desktop-S01 4. 别名冷却与回首选（F002／F008／F009）

- **WHEN** 用户通过别名发起请求或管理候选
- **THEN** 满足以下完整契约：

- 用户手动新增、排序、删除具体候选；允许同模型跨来源和跨模型，不自动扩充或改变顺序，不允许递归别名。每次调用固定配置、能力、消息和候选快照。
- 沿用五次临时故障尝试及 0.5／1／2／4 秒退避、32 MiB 暂存、成功后提交、停止优先和只重做当前 LLM 请求。限流／额度／认证不进入五次临时重试；具体模型的全局 reliability 仍按旧有效规则处理。

| 分类 | 成为冷却状态的条件 | 默认截止 |
| --- | --- | --- |
| transient | 临时网络／超时／408／5xx 等在本候选五次耗尽 | 失败完成后 60 秒 |
| rate-limit | RATE_LIMIT 或 HTTP 429 | 正的有效 providerRetryAfterMs 优先，否则 300 秒 |
| quota | QUOTA | 有明确有效服务端等待时间时采用，否则 3600 秒 |
| auth | AUTH／401／403／无效或缺失凭据 | 无自动截止，更换相关凭据／配置或手动重置后再试 |
| 本次不兼容 | 图片、上下文、参数、模型准备或其他确定性拒绝 | 本次跳过，不留下全局健康判断 |
| aborted | 用户停止、生命周期释放 | 不新建冷却、不切换候选 |

- 冷却只针对当前 Profile＋别名＋具体候选，不因一个候选失败跳过整个 Provider。临时失败是在本候选尝试耗尽后才开始计时；成功立即清除此候选故障计数。
- 一轮中首次成功候选被固定到 turn/end；后续工具循环先用它，失败后从其后继续查找本轮冻结队列中未失败／未冷却候选。该轮不因前面候选冷却到期而回跳。下一用户轮按原优先级寻找可用候选，到期的首选用该次真实请求尝试恢复；不等待冷却、不启动后台探测。
- 同一到期候选只允许一个恢复中的请求，其他并发会话继续备用；恢复成功释放租约，其他已开始轮次不强行切回。停止、异常和卸载均释放租约；迟到结果不能写健康或发布输出。
- 全部冷却／失败返回 ALL_CANDIDATES_FAILED，逐候选列出脱敏原因与可恢复时间；无限期认证阻断显示需处理凭据。没有可用候选时也不绕过冷却发探测。
- 页面显示当前故障、冷却剩余时间与“立即重新尝试首选”。此动作只清除该别名健康状态／恢复租约，不发模型请求、不改候选或凭据；下一轮才重试。动作带健康状态版本，防止覆盖刚完成的并发请求。
- 状态单独保存在实际 Profile 的插件数据目录 alias-health.json，不放 ManagerConfig／模型证据中。配置／候选／实际来源参数或凭据变化使相关旧状态失效；同一 Profile 多会话共享健康，跨 Profile 隔离。
